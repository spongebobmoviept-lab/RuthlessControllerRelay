# The development journey

This is not a changelog. It's a write-up of *why* this project exists, why it's built the way it is, how it was tested, and — in detail — every real failure encountered on the way here, including the ones that turned out to be wrong turns. The goal is that nobody who builds on this code has to rediscover the same holes by hand.

Everything below happened on real hardware, verified with real logs and real captured data. Where something was guessed instead of confirmed, that's said explicitly, because guessing is exactly what caused several of the bugs described here.

## Where this started

The motivating problem was narrow: a flight-sim-style game (originally, a specific title needing HOTAS-style joystick axis binding) has no native way to accept a regular gamepad's sticks as joystick axes. Windows treats "gamepad" (XInput/DirectInput) and "joystick" (also DirectInput, but a distinct device class most flight sims specifically look for) as different things, and there was no clean, single tool that could take a real PlayStation or Xbox controller and present it as a virtual joystick to one game while still behaving like a normal controller everywhere else — live-switchable, without a reboot or an unplug/replug cycle.

That narrow problem grew, over the course of real testing, into a broader one worth solving properly: reliably supporting whatever controller someone actually owns (PS4, PS5, Xbox, wired or wireless), with full rumble/LED/battery feedback wherever the hardware and connection type genuinely allow it, and doing it safely enough to hand to other people who are not developers and won't be debugging it themselves.

## Why C

A few concrete reasons, not just a stylistic preference:

- **Direct driver/Win32 API access.** Every piece of this — `SetupDiCreateDeviceInfoA` for creating root-enumerated devices, `HidD_*` for raw HID I/O, vJoy's C SDK, ViGEmClient's C ABI, `SRSetRestorePointW`, the registry APIs used to clean up HidHide's filter registration — is a native Win32/C API. Nothing here needs a managed runtime's marshaling layer in between.
- **Latency.** This runs a Sleep-free polling loop reading a controller at whatever rate the hardware allows, translating that into virtual-device writes, for as long as a game session lasts. A garbage-collected runtime's pause characteristics are a bad fit for a loop that's specifically tuned to avoid unnecessary work per iteration (see [Testing methodology](#testing-methodology) below for how seriously that tuning was taken).
- **Minimal runtime footprint for the audience.** This is meant to be handed to a non-developer friend as a single .exe that just runs. A native, statically-linkable build with no separate runtime installation requirement (built via [zig cc](https://ziglang.org/), a self-contained cross-compiling C/C++ toolchain — no Visual Studio install needed even on the build machine) matches that goal directly.
- **It matches its dependencies.** ViGEmClient is a C++ library with a C-callable ABI; vJoy's SDK is a plain C DLL interface. There's no impedance mismatch to manage.

## Core architecture

The single sentence version: **hide the real controller from every app but this one, then route data into whichever virtual device the game is supposed to see — never by adding or removing devices live, only by changing which one is currently receiving real data.**

Concretely, three independent pieces of driver engineering (all credited in full in [THIRD_PARTY_LICENSES.md](../THIRD_PARTY_LICENSES.md)) are combined:

1. **[vJoy](https://github.com/shauleiz/vJoy)** provides a virtual joystick device. A flight-sim's own axis-binding screen points at this, not at the real controller.
2. **[ViGEmBus](https://github.com/nefarius/ViGEmBus)** (via **[ViGEmClient](https://github.com/nefarius/ViGEmClient)**) provides a virtual Xbox 360 or DualShock 4 gamepad — the game's choice, live-switchable — for any game that just wants a normal controller.
3. **[HidHide](https://github.com/nefarius/HidHide)** hides the real physical controller from every process except this relay, for the entire time it's connected, in both modes. This is the single most important invariant in the whole design (see the incident below where it briefly wasn't) — a game must never be able to see the real controller *and* a virtual one simultaneously, since that's exactly the "mixed input" problem this whole architecture exists to prevent.

Both virtual devices are created once at startup and stay present for the entire session; only *which one is currently receiving real data* changes when the mode toggle fires. Device presence is never toggled live, because both HidHide and games in general handle live device add/remove far less reliably than they handle "this device has just gone quiet."

## Testing methodology

A few rules emerged, the hard way, over the course of this project, and were then followed deliberately for the rest of it:

- **Get real data before writing a parser.** Every raw-HID report layout in this project (DS4 Bluetooth, DualSense Bluetooth, DualSense USB, rumble/LED output reports for all four connection combinations) was confirmed against either real captured hardware data (a dedicated capture tool logging tens of thousands of live report samples while buttons/sticks were actively exercised) or real, working reference source (the Linux kernel's `hid-playstation.c`, DS4Windows's actual C# source — see [THIRD_PARTY_LICENSES.md](../THIRD_PARTY_LICENSES.md)) — never guessed from a spec sheet alone. Every single time a byte offset or bit was guessed instead, it was wrong (see the DualSense wired field-order bug and the original rumble/LED byte-layout guess below).
- **One change at a time, checkpoint before anything risky.** Full source snapshots were taken before any experiment with a real chance of regressing already-working, hardware-verified behavior, specifically so a bad experiment could be reverted to a known-good byte-identical state rather than trying to hand-undo it.
- **Real hardware over Windows Sandbox, for anything past install/uninstall.** Windows Sandbox was used — successfully — to prove the driver *install chain* works from a genuinely clean machine. It cannot do USB/HID passthrough at all, so it is structurally useless for verifying anything about actual controller input, hiding, or rumble. It also can't validate anything that depends on surviving a real reboot cycle, which is exactly the gap that let the worst incident in this project's history (below) go undetected until it happened on a real machine.
- **Revert immediately on any sign of instability, no exceptions.** Several experiments below (a second Bluetooth output handle, `WriteFile` for Bluetooth PS-controller output) were reverted the moment real-hardware testing showed instability, even when the underlying theory was reasonable and even when reverting meant leaving a feature unfinished.
- **Trust the OS's own logs over your own code's self-reported success.** The System Restore point bug below was only found by cross-checking Windows' own Event Viewer against this project's own success/failure reporting — which turned out to be wrong.

## Lessons from the field, in order

### The Bluetooth DS4 "no input at all" mystery → a new raw-HID input backend

A real DualShock 4 over Bluetooth (never USB or a dongle) defaults to sending a drastically reduced input report with almost no usable data. The fix for that part is well-documented in the community: read Feature Report `0x05` once to switch the controller into sending its full report. That alone was **not sufficient** — DirectInput's own HID-to-joystick translation simply cannot correctly parse the resulting large (547-byte) Bluetooth report; raw HID reads of the identical physical device showed live, correctly-changing data while DirectInput stayed frozen at all-zeros the entire time. This is a legacy DirectInput limitation, not anything wrong with the wake-up step or the controller — and exactly why community tools bypass DirectInput entirely for this case.

**Fix:** a dedicated raw-HID input backend that opens the device directly, performs the wake-up read, and parses the report itself — confirmed byte offsets (sticks, dpad+face buttons, shoulders, PS+touchpad+counter, triggers) checked against real captured data. DirectInput is still used for every case it already handles correctly (wired/dongle DS4, Xbox controllers, generic HOTAS devices) — this path only activates for the specific large-report Bluetooth case that was actually broken.

Two related bugs surfaced during the same real-hardware test round and were fixed immediately: a 16-bit signed integer overflow when negating a stick value sitting at its most-negative representable value (fixed by widening to `int` before negating and clamping), and a vJoy-specific left-stick inversion that turned out to only affect the Y axis, not X — confirmed by testing both directions independently rather than assuming symmetry.

### `capture_dualsense_raw()` and reverse-engineering DualSense over Bluetooth properly

Rather than guess DualSense's report layout by analogy to DS4, a dedicated capture tool logged roughly 17,500 real, live-changing Bluetooth HID reports while sticks and every button were cycled by hand. The resulting 78-byte report layout (stick axes, d-pad + face buttons, shoulders/triggers-digital, PS/touchpad + a report counter, analog triggers) was then implemented and confirmed correct against the same live data.

Two mistakes were made and caught during this same pass, worth remembering for anyone extending this further: sending DS4's Feature Report `0x05` wake-up probe "just to see" against a DualSense not only failed outright (DualSense doesn't recognize it) but appeared to destabilize the Bluetooth connection — removed entirely once DualSense's own `InputReportByteLength` was confirmed to already come back correctly without it. Separately, a capture tool's `ReadFile` failures were originally swallowed completely silently, meaning a full capture run could produce zero output with zero explanation — logging the real `GetLastError()` surfaced `ERROR_DEVICE_NOT_CONNECTED`, which is what correctly led to diagnosing DualSense's power-save idle-timeout behavior (below) instead of continuing to guess blindly.

### DualSense Bluetooth idle-timeout and the keep-alive discovery

On battery power alone, a DualSense's Bluetooth connection would go idle after a few seconds if nothing ever sent it an output report — confirmed directly: pressing the PS button wakes the lightbar for a few seconds, usable during that window, then it goes idle again. The fix is a single output report (report ID `0x31`, Sony's documented Bluetooth output report ID for this controller family) sent once at connection time, which alone "claims" the connection and stops the drop into idle — later hardened into a small standalone always-running keep-alive utility that re-sends this every few seconds, which also transparently handles the controller being power-cycled or re-paired mid-session with no reconnect-event detection needed at all.

### The out-of-bounds write in button remapping

The button-remap flow's button-capture helper could return a raw combined bitmask that matched no valid remap-table slot (e.g. a face button held alongside a trigger resting just past its click threshold) — and the code that consumed that result wrote to the resulting array index (`-1`) completely unconditionally, corrupting adjacent memory. Fixed at the root (the capture functions now only ever return a mask that maps to exactly one recognized slot; anything ambiguous is silently ignored and capture keeps waiting) with a defensive bounds check added at the write site too, specifically so this class of bug can't silently return even if some future caller bypasses the capture helpers.

### `setup_ds4_raw_hid()` matching the wrong Sony device entirely

The original raw-HID device matcher looked for "any Sony-vendor HID device with a large input report" — which also matches a DualSense or a PSVR2 Sense controller, both genuinely Sony-vendor devices with large reports but different report IDs entirely. Getting the wrong one meant the very first read failed, the connection tore down, and the exact same wrong device got grabbed again on the next attempt — an effectively unthrottled connect/disconnect loop with no visible error. Fixed by matching on the actual DS4 product IDs specifically, not vendor ID alone. **The lesson generalizes:** matching hardware by vendor ID alone is only ever safe when you've actually enumerated every device family that vendor ID covers.

### The critical incident: an uninstall step bricked keyboard and mouse system-wide

This is the single most serious failure in this project's history, and it's documented here in full because the failure mode is genuinely non-obvious and worth understanding if you're building anything that installs a Windows filter driver.

**What happened:** after running an uninstall step that removed HidHide's driver service and package, a real machine's keyboard and mouse stopped responding *entirely* — not just to this tool, to the whole operating system. No input at the login screen, in Safe Mode, or in the Windows Recovery Environment. BIOS-level input worked fine, ruling out a hardware fault. Recovery required building a bootable Windows installer USB on a separate machine, booting into it, loading the affected machine's offline SYSTEM registry hive, and by hand finding and deleting orphaned `UpperFilters`/`LowerFilters` registry values still pointing at the now-removed `HidHide` driver on the generic Microsoft HID device class (plus two other device-setup-class GUIDs) — roughly an hour of high-stakes manual recovery work, with no System Restore point available as a fallback at the time.

**Root cause:** HidHide's own driver installation registers itself as an `UpperFilters` entry on the device setup classes it needs to filter — including the *generic* HID class, which keyboards and mice also route through at a lower level (`kbdhid.sys`/`mouhid.sys` sit on top of the exact same `hidclass.sys` stack a game controller does). The original uninstall logic only ever removed HidHide's *service* and *driver package* — it never released that class-level filter registration. With the driver binary gone but the device class still configured to load it, Windows tried to load a now-nonexistent filter driver on every single boot, before login even runs — which blocks all keyboard/mouse input at the OS level, and neither Safe Mode nor WinRE helps, since both use the identical driver stack.

This exact gap had already been flagged once, in an earlier code-review pass, and wrongly rated as a *minor* issue — logged as roughly "if driver removal partially fails, the controller could stay hidden." That severity call was wrong, and the reason it was wrong is the actual lesson: **any gap in how a class-level HID filter driver gets uninstalled should default to high severity, because the blast radius is never scoped to the one device you're managing — it's the shared HID class stack every keyboard and mouse on the machine depends on too.**

**The fix, in full:**
- A registry-cleanup routine walks every subkey of the Windows device-class control registry, and for each one's `UpperFilters`/`LowerFilters` value, removes *only* the literal string `"HidHide"` (case-insensitive) — rewriting the value with every other entry preserved untouched (so an unrelated filter driver already present on the machine is never touched), or deleting the value outright if `HidHide` was the only entry. This is exactly the fix that previously had to be done by hand through an offline registry hive, now automated and scoped to nothing but that one literal string.
- A separate, read-only verification pass re-scans the same registry path afterward and explicitly confirms zero leftover references before ever suggesting a reboot — an uninstall that can't verify its own cleanup now says so loudly instead of silently inviting a reboot into the same failure.
- A plain "ask HidHide to stop enforcing while its driver can still respond properly" step (its own supported, documented mechanism) now runs first, as real defense-in-depth alongside the registry fix, not a replacement for it.
- A standalone, always-available, zero-elevation-required diagnostic command lets anyone independently check whether their own machine currently has any leftover HidHide filter-driver registry reference at all, without needing to trust this write-up or run a full uninstall to find out.
- **Windows Sandbox testing, however many times it's run, cannot catch this class of bug.** Sandbox is fresh every session and never persists a real reboot cycle after a real uninstall — this exact failure mode is structurally invisible to it, no matter how many Sandbox runs pass cleanly. That's now a standing rule for testing anything that touches a device-class filter registration.

**A mandatory Windows System Restore point before any install/uninstall action was added directly in response to this incident** — real, general-purpose OS-level rollback, as a second line of defense on top of the specific fix above, for whatever this class of tool gets wrong *next* that hasn't been found yet. Building that feature surfaced two more real bugs worth recording: the restore-point API has no timeout of its own and hung indefinitely on its very first real invocation on a machine that had never created a restore point before (fixed by moving the call to a worker thread with an enforced timeout); and a genuinely successful restore point could come back with sequence number `0`, which the original code wrongly treated as a failure sentinel (fixed by using `-1` as the actual failure sentinel and trusting the API's own status flag instead of the returned sequence number) — a bug only found by cross-checking Windows' own Event Viewer against this code's self-reported result, which is the reason "trust the OS's own logs" is listed as a standing testing rule above.

### Hiding was briefly, wrongly, tied to the mode toggle instead of connect/disconnect

The permanent, core invariant of this entire project is: the real controller is hidden from every app but this relay for the whole time it's connected, in *both* HOTAS and Normal mode — the mode toggle must only ever decide which *virtual* device is receiving real data, never whether the real hardware is hidden. An early implementation got this backwards: "Normal mode" literally meant cloak-off, i.e. the real controller fully visible to whatever game was running — exactly the "game sees the raw controller and a virtual one simultaneously" problem this whole design exists to prevent, and it survived multiple test rounds before being caught. Fixed by decoupling the two completely: hiding turns on once, the moment a controller is detected, and only turns back off when the relay actually stops — the mode toggle became a pure in-memory flag flip with no HidHide calls in it at all.

### vJoy devices silently accumulating across sessions

Repeated install/uninstall/reinstall testing left *two* duplicate, fully-functional vJoy device entries in Device Manager — nothing had ever cleaned up an old device instance before creating a new one. Manually removing one via the standard OS device-removal path itself left a child device orphaned in an "Unknown" state — direct proof that even the standard removal path doesn't fully cascade-clean in every case. The fix: a self-heal step that destroys every vJoy-identified device (matched broadly enough to catch both the root bus device and any stray orphaned child, found only after an initial version that matched too narrowly missed exactly this) at the *start* of every launch, before creating a fresh one — plus the same cleanup on every clean exit path (normal exit, fatal error, Ctrl+C, console close, logoff, shutdown). The stated guarantee is deliberately precise: a single exit-time cleanup can never be 100% relied upon (a hard crash or power loss skips it entirely) — the real guarantee is that a stale device from an unclean previous session can never survive past the *next* launch, and can never multiply.

### Two threading/memory-safety bugs found by a dedicated review pass, not by symptoms

A focused code-review pass (deliberately run before shipping, independent of any specific bug report) found two real concurrency bugs that hadn't yet produced an observed symptom:

- **A real double-free race** between the Ctrl+C handler (which fires on its own OS-spawned thread at any time) and the main loop's own end-of-session cleanup, both able to tear down the same virtual-controller client/target simultaneously if a disconnect and a Ctrl+C happened close together. Fixed with a proper critical section guarding both teardown and the per-frame device-write path.
- **Worker threads writing into stack memory that had already been freed.** Two different "run this blocking call on a worker thread with a timeout, and abandon the thread if it doesn't finish in time" patterns (the System Restore point calls, and a keep-alive diagnostic tool) passed a *stack-local* struct into the worker thread. On the timeout path, the calling function returns and its stack frame becomes invalid — but the abandoned thread is still running, and whenever its blocking call eventually completes (seconds or minutes later), it writes through what is now a dangling pointer into whatever currently occupies that stack address. This is exactly the kind of bug that produces a bizarre, seemingly unrelated crash report far later — fixed by heap-allocating those structs instead, and deliberately (and explicitly) leaking the allocation on the abandon path rather than risk freeing memory a zombie thread might still touch.

### Rumble, LED, and battery: reverse-engineered from real working source, not guessed

An initial attempt at PS-controller output (guessed byte offsets, based on incomplete public documentation) failed outright — `HidD_SetOutputReport` returned a generic failure code, and switching to a plain `WriteFile` call transported the bytes successfully but produced no visible effect on the real controller, because the guessed offsets themselves were wrong. The fix was to stop guessing and cross-reference two independent, real, working implementations: the Linux kernel's `hid-playstation.c` driver and DS4Windows's actual C# source (both credited in [THIRD_PARTY_LICENSES.md](../THIRD_PARTY_LICENSES.md)). That produced the exact, confirmed byte layouts for all four real combinations (DualSense USB, DualSense Bluetooth with its required CRC32 checksum, DS4 USB, DS4 Bluetooth) — each one worked immediately once implemented from a *confirmed* layout instead of a guessed one.

### A HidHide registration bug hid every controller on the machine at once

HidHide's own hide-list is additive and persists across process launches — it is not per-session state, which is a real, non-obvious property of how the driver works. A registration routine that only ever *added* to that list, without ever removing a stale entry, silently accumulated five separate hidden devices over the course of repeated connect/reconnect testing during the rumble work above — at which point every controller on the machine simultaneously stopped producing any input at all, system-wide, with zero warning. Fixed by having the same registration routine also unhide every entry that isn't the exact device path currently being (re-)registered, every time it runs. **Any future change to HidHide registration logic should be treated as a standing risk area for this exact failure mode.**

### The all-night freeze: a plausible theory that was completely wrong, and the real cause underneath it

This is the longest single debugging thread in the project's history, and it's worth reading in full because the eventual root cause had nothing to do with the feature being worked on at the time.

Adding rumble/LED output for PS controllers meant opening a second HID handle (for writing) alongside the handle already continuously reading input. The moment that second handle existed, live input froze solid — connects once, reads successfully exactly once, then never again, with no disconnect ever detected — identically across every input backend (DirectInput, and both raw-HID Bluetooth backends), regardless of whether the second handle was ever actually written to. This looked, reasonably, like a Windows/driver-stack limitation around opening a second handle to the same physical HID device while continuously reading from the first — and the fix applied at the time (remove the second-handle code entirely, accept that rumble/LED output isn't possible while input is being read from the same device) was reasonable *and correct as a description of what was tested*, but it turned out not to be the actual cause of the freeze at all.

**The freeze persisted even after every single line of the new rumble/LED code was fully reverted or disabled**, in a build with zero new code active — which is the only reason the real cause was ever found: a wired controller still froze, disproving the entire night's leading theory outright. The real clue had been quietly visible the whole time: Windows' own Game Controllers panel showed *two* duplicate entries for the one physical controller. A dedicated diagnostic tool that enumerated every matching DirectInput instance (instead of just the first, which is what the normal connection code had always done) confirmed it: two separate DirectInput instances existed for the one physical device, identical name/VID/PID, and one of them was a stale "ghost" node that could be successfully acquired and read forever but only ever returned the exact resting/center value of every axis — while the other was the real, live device. The leading theory for how the ghost node appeared: the same night's extensive raw-HID open/close and Bluetooth connect/disconnect churn from the rumble/LED testing itself — meaning the feature work likely *did* cause the bug, just not through the mechanism (a second handle) that had absorbed the entire night's attention while it was happening.

**Fix:** device enumeration now collects every matching candidate instead of stopping at the first, and when more than one exists, each candidate is acquired and given a short window to prove it emits at least one real HID data event — a genuine controller emits periodic reports at its normal rate even sitting perfectly still; a dead ghost node never does, no matter how long you wait. The first candidate that proves live wins.

**A second, closely related bug was found immediately while verifying the first fix**: HidHide's own device listing had the exact same "grab the first match" policy, and showed the identical class of duplicate — a stale Bluetooth device record that Windows still reports as "present" even though the controller is now connected over USB (a Bluetooth pairing record doesn't get removed just because the radio link isn't currently active). The tool had been silently hiding the *stale Bluetooth path* the entire time, leaving the real, currently-connected USB controller's HID interface completely unhidden and visible to every other application — silently defeating the entire point of HidHide for a plugged-in controller. Fixed by preferring a USB-rooted device path over a Bluetooth-rooted one when both are present.

**The general lesson, stated as a standing rule**: when a "nothing changed but it broke" bug shows up, check for duplicate device enumeration — in DirectInput's own listing *and* in HidHide's — before assuming the most recently-touched code is the cause. A whole night was spent correctly diagnosing and fixing one real bug (the second-handle freeze theory) while the actually-reported symptom had a completely different, unrelated cause the entire time.

### Re-testing wired PS-controller output after the real freeze cause was found

With the actual freeze root-caused to a stale ghost device rather than a second HID handle, it became worth re-testing whether a second, write-only (not read-write) handle for output could coexist safely with input on a *wired* connection specifically — a distinct, previously-untested mechanism from what had originally been blamed. It could: verified with continuous live input showing zero disruption, real lightbar color changes observed on the physical controller, and a deliberate two-minute stress test where a completely separate third process hammered the same physical device with 6,000 additional writes at roughly 50/second while the relay's own input logging kept showing continuous, live, correctly-changing values for the entire duration with zero freeze.

**Bluetooth PS-controller output remained disabled** even after this — the wired case's fix (a second handle, opened correctly) doesn't address what turned out to be a genuinely different failure mechanism specific to the Bluetooth transport, described in full in [docs/KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md).

### HidHide's JSON output has a real parsing gotcha, and two Xbox-specific bugs followed from it

HidHide's own device-listing command produces JSON-like text output. A parser that carved that output into per-device chunks by finding the next occurrence of a `"present"` field had a subtle bug: a device's `"friendlyName"` field appears in the output *before* that same device's `"present"` field — meaning the friendly name belonging to the *next* device in the list leaks backward into the *current* device's parsed chunk. When that next device happened to be vJoy's own entry (identifiable by its vendor string, itself just vJoy's author's name embedded in the driver, matching the credit in [THIRD_PARTY_LICENSES.md](../THIRD_PARTY_LICENSES.md)), a perfectly real, connected, gaming-capable Xbox controller got wrongly excluded as "that's actually vJoy" and its hiding registration was silently skipped. Fixed by also stopping each parsed chunk at the next `"friendlyName"` occurrence, whichever field comes first.

A second, related bug surfaced immediately once the first was fixed: retrying a failed hide-registration from the main loop, on a timer, could end up finding and hiding **ViGEmBus's own freshly-created virtual gamepad** instead of the real controller — a virtual Xbox-type target and a real Xbox-compatible controller both present, from the outside, as plausible "connected gaming device" entries with the same vendor/product shape, and nothing in the original matching logic could tell them apart once both existed. Fixed by moving the retry to run *before* the virtual target is created at all, so nothing exists yet to be confused with the real device.

### DS4-style rumble forwarding: a blocking call that only completes once a game sends data

Re-enabling rumble/LED forwarding for a DS4-emulated virtual pad — using the library's manually-polled "get current output state" call from the main input loop — froze wired PS5 input solid. Reading the client library's own source explained why: that call's underlying mechanism only completes once a real game actually sends a new output report, and it was being waited on with no timeout, on the same thread as the input read/relay loop. With no real game driving it during a manual test, the wait never completed and the whole relay hung on the very first call.

**Fix:** switch to the library's notification-callback API instead, which spawns its own internal background thread to perform that same blocking wait and only invokes a callback once a real notification genuinely arrives — never blocking the calling thread at all. (A related, easy-to-miss testing gotcha: a synthetic test tool driving the virtual pad directly, rather than a real game, needs to send output via `WriteFile` specifically — `HidD_SetOutputReport` is accepted by Windows without any error, but the virtual-gamepad driver's own notification mechanism never reflects values sent that way. A test tool that "succeeds" with the wrong API can waste real debugging time looking for a bug that isn't there.)

### Moving wired PS controllers onto a single shared input/output handle

Earlier work had already established that opening a *second* HID handle to the same wired PS controller — regardless of read/write mode — carries real risk (see the all-night freeze above; that specific finding was actually a false lead, but a genuinely separate, confirmed-safe re-test of a write-only second handle came later). The cleanest architecture, and the one real community tools for this exact problem (DS4Windows among them) use, is a single handle opened once with both read and write access, used for both the continuous input loop and for output writes.

Implementing this uncovered one more real bug: DualSense's wired USB report has a **genuinely different field order** than its own already-confirmed Bluetooth report — sticks and triggers, then a frame counter, then face buttons and d-pad, then shoulders, then PS/touchpad — not the same field order as the Bluetooth layout, and not the same as DS4's layout either. Guessing that the wired layout would match either of those failed immediately (buttons registered scrambled) and was only fixed by checking DS4Windows's real current source for the actual field order rather than continuing to guess.

### Bluetooth PS-controller rumble/LED output: investigated exhaustively, and deliberately left unsolved

This deserves its own detailed treatment — see **[docs/KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md)** for the full account, including testing across two entirely different Bluetooth radio chipsets and a from-source review of how other real tools handle (or fail to handle) the exact same problem. The short version: this was not abandoned from lack of trying. It's a genuine, currently-unsolved, community-wide problem, and Bluetooth PS-controller output stays disabled by design rather than shipped in a state that silently drops packets or destabilizes a Bluetooth link.

### The PS button as a mode-toggle trigger, and a smart first-run default

Raised as a direct question: since no game binds an action to the PS button (it conventionally just opens a system overlay), could it be used as the mode-toggle trigger instead of a standard button combo — and would that be genuinely safer than something like Back+Start, which, while chosen specifically because almost no game binds it either, is still a combo of two otherwise-ordinary buttons?

Checking `vigem_update()` (the function that builds what the game actually receives on the emulated gamepad) directly answered part of this: it only ever reads from the standard XInput-shaped button bitmask, and the PS button's pressed state has always lived in a separate variable specifically because it doesn't fit that bitmask. **The PS button was already completely invisible to whatever a game sees on the virtual gamepad in Normal mode, with zero code changes needed** — a nice example of an existing design decision (keeping PS/touchpad state outside the standard bitmask, made for an unrelated reason — see the DS4 PS button/touchpad support work) turning out to also solve a problem it wasn't originally built for.

What was actually missing was narrower: the toggle-combo mechanism only recognized the standard XInput button set, because it was checked against `gp.wButtons` alone and parsed through its own separate, deliberately narrower table (`NAMED_BUTTONS`) than the one the button-remap system used (`NAMED_PHYS`, which already included the PS button, touchpad, and trigger clicks). The fix consolidated the two: the toggle combo now shares `NAMED_PHYS` and is checked against the same combined wButtons+trigger+PS+touchpad mask the button-remap capture flow already built, removing a redundant table rather than extending two tables in parallel. `g_toggle_button_mask` widened from a 16-bit `WORD` to a 32-bit `DWORD` to hold the extra bits (`PHYS_PS_BUTTON`/`PHYS_TOUCHPAD` live at bits 18/19, well outside the 16-bit XInput button range, so there's no collision).

One more real behavior was added on top, not just "make it parseable": when the PS button (or touchpad) is configured as the toggle, a press of it is now explicitly excluded from also being forwarded as a normal vJoy button — otherwise pressing it to switch modes would simultaneously fire whatever vJoy button it happens to be mapped to (PS is vJoy button 17 by default), a confusing double-duty press. This is scoped narrowly to just the PS button and touchpad specifically — standard buttons like Back and Start still work as ordinary vJoy buttons even while also serving as the toggle combo, exactly as they always have, since changing that more broadly wasn't asked for and carries real risk of surprising an existing setup that relies on the current behavior.

**A smart first-run default was added as a follow-up**, since a global hardcoded default can't be "the PS button" for everyone — an Xbox controller has no equivalent button this software (or any XInput-based software) can even see, so defaulting everyone to the PS button would silently strand Xbox-only users with no controller-side toggle at all. Instead: a genuinely fresh install (no config file exists yet) defers the real decision until the very first controller actually connects, then upgrades the default to the PS button only if that first controller is a real PlayStation pad — an Xbox-first connect leaves Back+Start exactly as it already was. This decision fires at most once, ever, and is skipped entirely the moment a config file already exists for any reason (a previous run's decision, or a friend's own hand-edited or `R`-captured choice) — an existing setup is never silently overridden.

**Verification, stated honestly:** the parsing/formatting/config-round-trip logic for this is covered by new cases in `--test-config` (a real, runnable regression test, not just code review — see [Testing methodology](#testing-methodology)), and the full build compiles clean with zero warnings. **The live behavior — pressing the PS button on a real controller and confirming it both triggers the mode switch and never leaks through to a game — has not yet been verified on real hardware at the time of writing.** Treat it as implemented and self-tested at the logic level, not yet confirmed end-to-end the way most of the rest of this document's findings are.
